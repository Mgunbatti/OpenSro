# SEC-001: Blowfish encryption does not pad buffers shorter than 7 bytes

- Original: `CBlowFish::Encrypt` 0x493b50 (GatewayServer)
- Rewrite: `CBlowFish::Encrypt` in `JMX_Library/BSNet/security/BlowFish.cpp`
- Severity: minor

## What the original does

The buffer is processed in 8-byte blocks up to the length rounded up to 8. A block counts as the
last, partial one when `pos >= len - 7`, compared unsigned. For `len` 0 to 6 the subtraction
wraps to a value near 4 GB, the test never holds, and the single block goes through the
full-block path: in copy mode all 8 bytes are read from the source, in place nothing is
cleared. From 7 bytes on the tail is zero-filled as intended.

The stream socket encrypts `payload + 4` bytes, so every packet with a payload of 0 to 2 bytes
takes this path.

## Effect

The padding of short packets is whatever followed the data in the source buffer (old bytes of a
pooled message) instead of zeros, and up to 7 bytes (4 on the socket path) are read past the requested length. The
receiver decrypts and ignores the padding, so the protocol still works; stale buffer contents
travel encrypted on the wire.

## Fix

Compare signed or test `pos + 8 >= len` so that the last block is always zero-padded.
